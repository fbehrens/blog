Lesson 08 · reading runtime evidence

Browse telemetry

Spans are in motel — now read them. Three ways into the same SQLite store: a terminal TUI for eyeballing, an HTTP/JSON API for scripting, and an MCP surface for AI agents. The point isn't the tool; it's the habit — debug from runtime evidence, not from guesses.

The single win for today Read a trace as a waterfall: a tree of spans with durations. Where the tree branches tells you what called what; where time pools tells you where to look; what repeats tells you what's wasted.

2 · The HTTP API — script it

Everything the TUI shows is plain JSON over HTTP — perfect for a quick curl or a CI assertion. The full spec is at /openapi.json; the endpoints you'll actually use: 

GET /api/health                       # liveness {"ok":true,...}
GET /api/services                     # {"data":["skillman", ...]}
GET /api/traces?service=skillman      # recent traces (root op, duration, spanCount)
GET /api/traces/<trace-id>             # full tree → data.spans[] with depth + durationMs
GET /api/spans/<span-id>               # one span + its logs
GET /api/logs?service=skillman        # recent correlated logs
GET /api/traces/search?...            # structured search

A trace detail comes back as a flat spans[], each carrying a depth — so rendering the tree is a one-liner:

TRACE=$(curl -s "127.0.0.1:27686/api/traces?service=skillman" \
  | python3 -c "import json,sys; print(json.load(sys.stdin)['data'][0]['traceId'])")

curl -s "127.0.0.1:27686/api/traces/$TRACE" | python3 -c "
import json,sys
d = json.load(sys.stdin)['data']
print(d['rootOperationName'], d['durationMs'], 'ms', d['spanCount'], 'spans')
for s in d['spans']:
    print('  '*s['depth'] + f\"{s['operationName']:<22} {s['durationMs']:>3}ms [{s['status']}]\")
"

3 · What skillman's link actually looks like

That query, run against a real link git, prints the tree below — and it is exactly the shape of the code that produced it:

cli.link                11ms  [ok]
  Skills.link              9ms  [ok]
    Skills.sourceOf          8ms  [ok]
      Skills.realFolders       8ms  [ok]
    Skills.linked            1ms  [ok]
      Project.root             1ms  [ok]
    Project.root             0ms  [ok]
Read it like a detective Shape = call graph: cli.link → Skills.link → resolve the source, check what's linked, then write. Time pools in sourceOf → realFolders (8 of 11 ms — it readDirectorys and stats the skills dirs). Repetition is the tell: Project.root appears twice — once under Skills.linked, once directly. The .git walk runs twice per link. A code review glanced past it; the waterfall makes it obvious.

The lesson under the lesson

That duplicate Project.root is the whole reason telemetry earns its keep. The tests are green, the code reads fine, the output is correct — and yet the trace shows wasted work. Hermetic unit tests prove correctness; traces reveal behaviour. (The fix, for later: memoize the project root, or thread skillsDir down instead of re-deriving it. Don't fix it from a guess — fix it, then re-read the trace and confirm the second Project.root is gone.)

4 · For your AI agent

motel ships a motel-debug skill and an MCP server (motel-mcp) that expose the same /api surface to coding agents — so an agent can pull a trace and reason about runtime behaviour instead of hallucinating it. Install once and any future session can query your local telemetry: 

npx skills add kitlangton/motel --skill motel-debug      # project-local
npx skills add kitlangton/motel --skill motel-debug -g    # global

Privacy note: the store is local but real. Correlated logs can contain secrets/PII and AI traces can contain full prompt text — treat ~/.local/state/motel/telemetry.sqlite as sensitive dev data.
