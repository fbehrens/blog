The Config service

First real service in your skill-manager. It owns one question — where is skills_root? — and answers it so completely that no other module ever learns the answer came from an env var. Built on the ConfigProvider default service from Lesson 4, TDD'd, with a one-line test seam.

The single win for today Read config once, at layer-build time, fail the whole app if it's missing, and test both the happy path and the fail-fast path without touching process.env — by swapping the ConfigProvider underneath.

The toolkit reads; your service packages the reads into a named thing the rest of the app depends on.

The reading primitive

Config.string("SKILLS_ROOT") returns a Config<string> — which is an Effect<string, ConfigError, never>. R is never because it reads from the ambient ConfigProvider, a default service (Lesson 4) — real process.env in production. It fails with ConfigError, and the error names the missing key — remember that, the fail-fast test relies on it. 

// effect/Config.d.ts
declare function string(name?: string): Config<string>
declare function int(name?: string): Config<number>
declare function boolean(name?: string): Config<boolean>
// + withDefault, option, nested, orElse, map, all — for when one env var isn't enough

The service (your real code)

// packages/skillman/src/config.ts
import { Config as EffectConfig, Context, Effect, Layer } from "effect"

export interface Interface {
  readonly skillsRoot: Effect.Effect<string>
}

export class Service extends Context.Service<Service, Interface>()("skillman/Config") {}

// Resolve the env var ONCE at layer construction. If SKILLS_ROOT is missing,
// the layer BUILD fails (ConfigError) — the app refuses to start mis-configured.
export const layer: Layer.Layer<Service, EffectConfig.ConfigError> = Layer.effect(
  Service,
  Effect.gen(function* () {
    const skillsRoot = yield* EffectConfig.string("SKILLS_ROOT")
    return Service.of({ skillsRoot: Effect.succeed(skillsRoot) })
  }),
)
Two design decisions worth pausing on 1 · Read at build time, not call time. The yield* Config.string runs once when the layer is constructed. The interface exposes skillsRoot as an already-resolved Effect.succeed, not a fresh read. So a misconfigured app dies at startup, not on the 500th request.

2 · The ConfigError is in the layer's error channel (Layer.Layer<Service, ConfigError>), not buried inside a method. Building the app surfaces the failure; the type even tells you it can happen.

The test seam: swap the provider, not the env

Here's the Lesson-4 payoff. ConfigProvider.fromEnv({ env }) builds a provider backed by a fixed map instead of real process.env. ConfigProvider.layer(provider) installs it. Provide it under your Config.layer and the whole stack reads from your fake — no global mutation, no vi.mock, no leakage between tests. 

// packages/skillman/src/config.test.ts
import { describe, expect, it } from "@effect/vitest"
import { ConfigProvider, Effect, Layer } from "effect"
import * as Config from "./config.ts"

// Config.layer, fed a fake env map underneath — same shape as a defaultLayer.
const configWith = (env: Record<string, string>) =>
  Config.layer.pipe(Layer.provide(ConfigProvider.layer(ConfigProvider.fromEnv({ env }))))

describe("Config", () => {
  it.effect("reads skillsRoot from SKILLS_ROOT", () =>
    Effect.gen(function* () {
      const config = yield* Config.Service
      expect(yield* config.skillsRoot).toBe("/home/me/skills")
    }).pipe(Effect.provide(configWith({ SKILLS_ROOT: "/home/me/skills" }))))

  it.effect("fails when SKILLS_ROOT is missing", () =>
    Effect.gen(function* () {
      // Effect.flip moves the error into the success channel so we can assert on it.
      const error = yield* Effect.gen(function* () {
        const config = yield* Config.Service
        return yield* config.skillsRoot
      }).pipe(Effect.provide(configWith({})), Effect.flip)
      expect(String(error)).toMatch(/SKILLS_ROOT/)
    }))
})
An honest TDD note The fail-fast test passed the moment it was written — Config.string already errors with the key name, so this test didn't drive code, it locks the contract. That's a legitimate use of a test: pin behaviour you depend on (the error mentions the key) so a future refactor can't silently break it. Just be honest with yourself about which tests are tracer-bullets and which are guardrails.

Why fromEnv({env}) beats vi.mock here

vi.mock(process.env)

Global mutation. Tests leak into each other, order matters, and the mock is untethered from the real type — exactly the "foot armada" from Lesson 3.

ConfigProvider.fromEnv({env})

A value you pass in. Each test builds its own provider, scoped to its own layer. No globals, no reset hooks, type-checked end to end.
Run it 
bun test packages/skillman   # 2 pass — happy path + fail-fast, no real env touched
bun run check                # clean — ConfigError shows in the layer's type
Then poke it: change "SKILLS_ROOT" in config.ts to "SKILLS_DIR" and watch the happy-path test fail with a ConfigError naming SKILLS_DIR — the read and the test env drifted apart, and the failure tells you exactly which key.

Where this slots in

Config is leaf 1 of skillman's four services. It depends on nothing but the ConfigProvider default, so it sits at the bottom. Next come Project (walk cwd up to .git, expose the project's skills dir — needs FileSystem + Path), then Skills (the domain heart: available / linked / link / copy — needs Config + Project), then a thin Cli. Each is a swappable layer; each gets the same fromEnv-style test seam in its own dimension.
