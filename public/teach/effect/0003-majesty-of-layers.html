Lesson 03 · The mental model

The majesty of Layers

Distilled from Kit Langton's “Effect and the Near Inexpressible Majesty of Layers.” He wrote opencode and motel — the two tools this whole course orbits. This is the canonical framing of what you've been practicing.

In Lessons 1–2 you built a service and tested it by swapping its layer. This lesson gives you the why — one mental model that makes all of it click: a service requirement is just a function parameter, tracked in the type system. Once you see that, dependency injection and testing stop being magic.

The single win for today Read Effect<A, E, R> fluently — especially the third slot R — and explain why providing a test layer is strictly safer than vi.mock. Backed by a runnable coinFlip in your playground.

First, the pain: what vi.mock can't see

The article opens with a surge-pricing function tested via vi.mock. Four footguns, all invisible to the type checker:

// 1 · misspell the file → mock silently misses, real code runs
vi.mock("./future-flaps", () => ({ isEnabled: vi.fn() }))

// 2 · misspell the function → you mock an imaginary export
vi.mock("./feature-flags", () => ({ isEnable: vi.fn() }))

// 3 · wrong return type → type-checks anyway (mocks are untethered)
vi.mocked(isEnabled).mockResolvedValue("sure")   // boolean expected

// 4 · the dependency is INVISIBLE in the signature
export const getPrice = async (basePrice: number): Promise<number> // ...needs flags? who knows
“This isn't just a footgun — it's a foot armada.” The signature of getPrice gives no indication whatsoever of its dependence on feature flags. Nothing at the type level apprises us of it.

The fix: requirements live in the type

When you yield* a service, Effect adds it to the effect's third type parameter. The dependency becomes impossible to forget — the compiler won't run the program until you provide it. 

Effect.Effect<string, never, Random>
//            ^^^^^^                 A — what it succeeds with
//                    ^^^^^          E — how it can fail
//                           ^^^^^^ R — what it REQUIRES (the services)
The one analogy to keep A requirement is a function parameter. Providing a layer is passing the argument. 
const useConfig: (config: Config) => string       // requires Config
const useConfig: Effect<string, never, Config>    // ...same thing, third slot

useConfigFn(config)                               // arg eliminates the requirement
effect.pipe(Effect.provide(configLayer))          // layer eliminates the requirement
One difference: calling a function runs it now; Effect.provide just satisfies the requirement — nothing runs until you execute the effect. (Think of a function closed over its arg in a thunk.)

Tag & Layer, in two breaths

Tag = effectful interface

The service's name + shape, no implementation. “What”, never “how”.

Layer = effectful constructor

Builds the implementation. Layer.succeed for a ready value; Layer.effect when construction itself needs other services.

The runnable example: coinFlip

One interface, two implementations — a real one and a fixed one for tests. No mocking anywhere.

export class Random extends Context.Service<Random, {
  readonly nextNumber: Effect.Effect<number>
}>()("playground/Random") {}

export const randomLayer = Layer.succeed(Random, {
  nextNumber: Effect.sync(() => Math.random()),
})
export const fixedRandomLayer = (n: number) =>
  Layer.succeed(Random, { nextNumber: Effect.succeed(n) })

export const coinFlip: Effect.Effect<string, never, Random> = Effect.gen(function* () {
  const random = yield* Random            // ← this adds Random to the R slot
  const n = yield* random.nextNumber
  return n > 0.5 ? "heads" : "tails"
})

Testing is just providing the fixed layer — deterministic, type-safe, four lines:

const flipWith = (n: number) =>
  Effect.runPromise(coinFlip.pipe(Effect.provide(fixedRandomLayer(n))))

expect(await flipWith(1)).toBe("heads")   // 1 > 0.5
expect(await flipWith(0)).toBe("tails")
Run it — it's in your playground 
cd playground
bun test            # 5 pass — coinFlip + skills, no mocks, no real disk/RNG
bun run check       # clean
Then prove the safety claim yourself: open coinflip.test.ts, delete .pipe(Effect.provide(fixedRandomLayer(n))), and watch bun run check fail with “Missing 'Random' in the expected Effect context.” The forgotten dependency is a compile error, not a 2 a.m. production page.
Effect 3 → Effect 4 (your stack) The article is written in Effect 3. Two mechanical swaps and everything else is identical: 
// tag
Context.Tag("Random")<Random, Shape>()        // 3.x
Context.Service<Random, Shape>()("Random")      // 4.x  ← you use this

// traced fn — 4.x wants a name (and that name becomes a span — see telemetry lesson)
Effect.fn(function* () { … })                  // 3.x
Effect.fn("Pricing.getPrice")(function* () { … }) // 4.x

Under the hood (one paragraph)

The runtime threads an ambient Context — basically a Map<string, any> — through every effect. The tag's string ("playground/Random") is the map key. yield* Random just looks up that key; a layer just writes to it. It sounds unsafe, but it's correct by construction: yielding a tag adds its type to R, providing a layer removes it, and the layer constructors are constrained to match the tag's interface. If your program type-checks, every lookup is guaranteed to hit, with the right type.
